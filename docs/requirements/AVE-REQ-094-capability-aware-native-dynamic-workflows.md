# AVE-REQ-094 — Capability-aware native dynamic workflows

## Intent
Serves [GOAL-009](../PRODUCT.md#product-goals) through [AVE-FEAT-019 — Autonomous implementation workflow](AVE-FEAT-019-autonomous-implementation-workflow.md). Origin clauses in the user brief:
- [U27](../../ai-video-editor-requirements/intake/USER_BRIEF.md#u27) — Use the already-created Claude Code project bootstrap and implement through dynamic, self-improving, optimally adapted workflows.

Imported from the immutable baseline [AVE-REQ-094](../../ai-video-editor-requirements/spec/requirements/AVE-REQ-094.md) (package v1.0); primary gate M0, scope v1.

## Description
Claude Code shall use task-specific native dynamic workflows where actually available, with a documented bounded fallback to subagents or sequential execution.

## Acceptance criteria
- [ ] AC-1 Probe the current environment for workflow tools, available models, subagents, worktree isolation, permissions, hooks, network, browser tools, CPU/RAM, and accelerator access.
- [ ] AC-2 When native workflows are available, compose requirement-specific investigation, implementation, testing, and independent review with structured handoffs and dependency-aware parallelism.
- [ ] AC-3 Validate native workflow syntax against the installed runtime; do not invent APIs or assume a published feature is enabled in this cloud session.
- [ ] AC-4 When unavailable, perform the same lifecycle through bounded subagent/sequential tasks; do not build a custom orchestration platform instead of the editor.

## Edge cases
- Workflow tool, subagents or worktrees unavailable → documented sequential or subagent fallback (AC-4);
  without subagents the independent review runs in a fresh session (or a context holding nothing of the
  implementation work) from the repository alone, the Status log records it as a sequential review, and the
  requirement stays `verification` until that review is recorded (AC-4).
- A capability that changes between sessions (network policy, credentials, tools) → re-probed with
  `scripts/probe-environment.sh` and recorded (AC-1): `resume-project` step 6 runs the probe with `--offline`
  at every resume, and a run without `--offline` re-measures the network lines, which the header of
  `docs/ENVIRONMENT_CAPABILITIES.md` asks for after a session restart.
- Workflow syntax or a feature not present in the installed runtime → never assumed (AC-3).
- Built-in FFmpeg hardware encoders without a device → reported as no accelerator (AC-1): the probe prints
  `accelerator: none (no device)` when the device directory shows no character device with the name of a GPU
  node and `nvidia-smi` reports no GPU.
- Entries of `/dev` → one walk over the entries of `/dev` and of `/dev/dri` gives the two device lines and the
  verdict, and it judges each name as one string, so a name that holds a line feed or a space stays one name
  (AC-1). A GPU node is a character device, directly or behind symbolic links, whose whole name is `nvidia<N>`
  or `dri/renderD<N>`, where `<N>` is one or more of the digits 0 to 9; it counts when this user can open it
  for reading and for writing. Every other entry counts for nothing: a driver control node (`nvidiactl`,
  `nvidia-uvm`, `nvidia-modeset`), a display-only node (`dri/card<N>`), a directory, a regular file, a FIFO, a
  block device, a dangling link, a name with a prefix or a suffix (`xnvidia0`, `nvidia0.txt`,
  `dri/card-renderD128`, `renderD128.bak`, `nvidia0` followed by a line feed and more text), `nvidia<N>`
  inside `dri` and `renderD<N>` outside it. The device lines list the entries named `nvidia*` and the entries
  of `dri`, hidden ones and those behind a linked `dri` included, each as one word: a path the shell would
  quote stands in the form of `printf %q`, on the device lines and in the verdict alike. No other entry of
  `/dev` is listed. A device directory that is missing, or that this user cannot list, reads as one without
  entries.
- A GPU node that this user cannot open → `accelerator: none (no access to <node>)`; beside a node that opens,
  the verdict names the open one alone (AC-1). The probe opens a node through one `dd` call with
  `count=0 conv=nocreat,notrunc`, for reading and for writing: the call creates and truncates no file and
  transfers nothing, so a run leaves the device directory as it was. Without a `dd` that takes these operands
  (GNU coreutils; the probe tries them on `/dev/null`) no node is opened, and a GPU node then reads
  `accelerator: unknown (open test unavailable for <node>)` unless `nvidia-smi` lists a GPU.
- `nvidia-smi` installed without a driver or a device (a CI image, a container started without GPU access) →
  no accelerator (AC-1): its answer counts only when it exits 0 within its time limit (10 s, killed 2 s later
  when it ignores the signal) and prints on its standard output a GPU row: a name, a comma, a memory figure
  with the unit, and the end of the line (`<name>, <n> MiB`; the name may hold a comma and holds one character
  or more besides commas and spaces). A driver diagnostic, a failure, a query that hangs, an empty answer, a
  diagnostic with exit 0, a row without a name, a row with text behind the unit or a row on the error stream
  leaves the verdict to the device nodes. Without a `timeout` command the query is left out and the line reads
  `no GPU reported (timeout unavailable)`. `AVE_PROBE_SMI_TIMEOUT` replaces the 10 s only as a positive whole
  number (digits alone, one of them above 0); any other value leaves the 10 s. The limit covers `nvidia-smi`
  and its process group: a process that `nvidia-smi` starts in a session of its own and that keeps the output
  open holds the probe until that process ends, which is a limit of the probe.
- What `present` means → a GPU device node opens, or `nvidia-smi` lists a GPU: the probe opens a node and sends
  it nothing. A render node of a software or virtual DRM driver therefore reads `present`, and whether an
  encoder or a model runs on a device is measured by the requirement that uses it (AVE-REQ-076, AVE-REQ-066);
  `docs/ENVIRONMENT_CAPABILITIES.md` records this limit (AC-1).
- A container with a CPU or memory quota → the `cpus` and `memory` lines print the kernel's totals, and the
  lines `cpu quota (cgroup v2)` and `memory limit (cgroup v2)` print the limits of the cgroup mounted at
  `/sys/fs/cgroup`, which inside a container with a cgroup namespace of its own is the container's cgroup
  (AC-1). `cpu.max` holds a quota or `max`, a space and a period above zero, and `memory.max` holds a number
  of bytes or `max`, each with one line end at most: a quota reads as the quota divided by the period in CPUs
  and a byte count as GiB, each followed by the file's content; `max` and a missing file read `none`; any
  other content reads `unknown`. The two lines read these two files alone: a limit set on a parent cgroup
  outside that namespace, the cgroup of a process below the root of the mount (a container that shares the
  host's cgroup namespace) and a cgroup v1 hierarchy stay unread, and such a quota reads `none`.
- A probe line fixed to the value of the host that runs the suite → fails the suite (AC-1): fixture inputs that
  differ from the host (a fake `getconf` and `id`, `AVE_PROBE_PROC_DIR`, `AVE_PROBE_CGROUP_DIR`,
  `AVE_PROBE_ROOT`) show that the CPU count, memory, CPU model, cgroup, OS user and writability lines are
  computed.
- No `claude` command where the probe runs (the development container) → reported as not installed; the
  version row comes from `claude --version` on the host (AC-1).
- A deny rule of the project settings → recorded as enforced only after an attempted denied command was
  refused (AC-1).
- A media tool or toolchain absent from PATH (`ffmpeg`, `ffprobe`, `python3`, `uv`, `node`, `pnpm`, `git`,
  `docker`) → its line reads `not installed` (AC-1).
- The probe started outside the repository, or through a relative path while `CDPATH` is exported → the disk,
  Git and writability lines still measure the repository that holds the probe (AC-1).
- A host that answers the HEAD request, with a 3xx, 4xx or 5xx status as well as with a 2xx → `HTTP <code>`;
  no response within 10 s (refused, unresolved, TLS failure, timeout) → `unreachable`; the request is
  header-only, so a large body such as the pypi simple index never decides the verdict (AC-1). No `curl` →
  `curl not installed`; `--offline` → the probes are skipped and `curl` is never invoked (AC-1).
