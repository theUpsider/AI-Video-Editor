# AVE-REQ-097 — Verification gates that cannot pass as placeholders

## Intent
Serves [GOAL-009](../PRODUCT.md#product-goals) through [AVE-FEAT-019 — Autonomous implementation workflow](AVE-FEAT-019-autonomous-implementation-workflow.md). Origin clauses in the user brief:
- [U27](../../ai-video-editor-requirements/intake/USER_BRIEF.md#u27) — Use the already-created Claude Code project bootstrap and implement through dynamic, self-improving, optimally adapted workflows.
- [D03](../../ai-video-editor-requirements/intake/USER_BRIEF.md#d03) — Derived correctness requirement: exact timing semantics, rendered-output evidence, shared composition model, and honest verification.

Imported from the immutable baseline [AVE-REQ-097](../../ai-video-editor-requirements/spec/requirements/AVE-REQ-097.md) (package v1.0); primary gate M0, scope v1.

## Description
Replace bootstrap-only verification with staged real checks and independently verifiable release gates as implementation begins.

## Acceptance criteria
- [ ] AC-1 Keep a fast feedback tier, real-media integration tier, and full release tier behind documented repository commands.
- [ ] AC-2 Tie verification evidence to a commit/tree fingerprint, configuration, requirement IDs, and test results; stale evidence cannot certify changed code.
- [ ] AC-3 Use supported hooks only after a small smoke test; avoid recursive Stop-hook loops and repeated full renders on every conversational response.
- [ ] AC-4 No-op scripts, skipped integration tests, caught exceptions returning success, or provider mocks cannot establish completed product requirements.

## Edge cases
- A skipped, expected-to-fail or never-collected test → fails verification or gives no evidence (AC-4); this holds for a module skipped at collection (`pytest.skip(allow_module_level=True)`, `pytest.importorskip`), for a selected test that never ran (`pytest.exit` with status 0, `--collect-only`, `--setup-plan`: the session fails under `--forbid-skips`) and for the tooling unit tests (`scripts/evidence.py unittest` also fails a file without tests, a test that returns a value such as a generator or a coroutine, and a tag that stands above no test that ran).
- A test that exists and did not run in a tier (deselected by the tier's marker expression, or a tooling file without a suite result of the run) → recorded as `not-run`: it evidences nothing, `show --require-complete` exits 1 for a requirement with such a test, and the release tier, which runs every test, fails a `done` requirement that has one (AC-4).
- A pytest step that passed without a report holding executed tests (the session ended early, or the recorder was blocked) → the step fails (`evidence.py check-report`); blocking the recorder is a usage error (AC-4).
- A comment tag in a file of `scripts/tests/` that is neither a suite `scripts/tests/run.sh` lists (one `run_suite` line at the start of a line) nor a `test_*.py` file of that directory → stops `record` and `check-done` with the file and line, in every tier: the runner itself, a fixture builder, a suite named only in a comment of `run.sh`, a Python helper and a file in a subdirectory have no suite result, so no run could evidence such a tag. Files inside a `__pycache__` directory are left out. A listed suite or a unit-test file that fails → counts against every criterion it tags (AC-4).
- A listed tooling suite that exits 0 without running a check (no `TOTAL: pass=N fail=M` line with N ≥ 1) or with a failed check in that line (M ≥ 1) → `run.sh` fails and the suite counts against every criterion it tags; `test-checker.sh --all-awks` fails when it ran no awk implementation, and without `jq` or `node` the suite stops with status 2 before any case (AC-4).
- A suite result in the run directory that names no tooling test file of this tree, carries another name than its file's, or other tags than the file's comment lines → stops `record` and `check-done` (AC-2, AC-4).
- A test tagged with a criterion that does not exist → stops the test run; a tooling test comment tag of that kind fails the "Evidence manifest" step of every tier and `check-done`, naming the file and line (AC-2).
- A requirement file whose ID has more digits (`AVE-REQ-0180`) → a requirement of its own, never a stand-in for `AVE-REQ-018`; two files with one ID stop the evidence tool (AC-2).
- A manifest that names a requirement without a working file → `evidence.py show` reports the unknown ID as an error, with or without requirement IDs on its command line (AC-2).
- A run with a failed step → certifies no requirement complete: `evidence.py show --require-complete` exits 1, also when a newer run of a lighter tier passed on the same tree (the heaviest fresh run decides, and a failed fresh run of any tier counts, with or without `--tier`) (AC-4).
- Evidence recorded for an older tree or another toolchain (media tools, installed backend packages) → reported stale and refused where freshness is required (AC-2).
- A local state of the repository that hides an edit from Git (an index flag such as assume-unchanged, skip-worktree or fsmonitor-valid, a filter or ident attribute, a line-end conversion, an ignore rule outside the `.gitignore` files, an fsmonitor hook, Git configuration that the caller adds through `GIT_CONFIG_COUNT` or `GIT_CONFIG_PARAMETERS`) → changes no entry of the fingerprint: an entry holds the mode of the index entry or `untracked`, the executable bit and the raw bytes of the working file, for every index entry and every untracked file that no `.gitignore` file ignores. The edit changes the fingerprint, the Stop gate runs `verify.sh` and recorded evidence reads stale (AC-2, AC-3).
- A tree with a gitlink, an embedded repository, a listed path that begins with a double quote, holds a line feed or ends with a carriage return, a listed file that cannot be read, or a failing Git listing → keeps no fingerprint: the Stop gate runs `verify.sh` there and no evidence is fresh. A symbolic link enters with its link text; the file it points to outside the listed paths is local state. Staging a new file changes its entry from `untracked` to its index mode, so a run that should stay fresh after the commit starts with its new files staged ([ASM-024](../ASSUMPTIONS.md)) (AC-2, AC-3).
- A test file or `conftest.py` that Git ignores → stops the pytest session: the plugin asks `git check-ignore` about every collected test file and every loaded `conftest.py` inside the tree. Inside a repository (a `.git` entry in the tree's directory or in one above it) a Git that ends `git check-ignore` with another status than 0 or 1, or that does not start, stops the session too; a tree without a repository is the one case in which Git is asked nothing (AC-2, AC-4).
- A file of the tree that the fingerprint does not name → fails the step "No file outside the fingerprint and the listed paths" of every tier, unless the list of ignored paths in `scripts/verify.sh` admits its path. Such a file is one that a `.gitignore` rule ignores (a `backend/ave.pyc`, which pytest imports ahead of the product package; a `.gitignore` in a subdirectory that lists itself beside a `mypy.ini`, a `ruff.toml` or the target of a link; a `conftest.py` in an ignored directory), one inside a directory named `.git` below the root, or a FIFO: Git lists the last two nowhere. The step walks the tree and compares it with the listing of the fingerprint, so it holds no rule per form. The list admits eight directories (`var`, `data`, `.claude/worktrees`, `.serena`, `backend/.venv`, `backend/.pytest_cache`, `backend/.ruff_cache`, `backend/.mypy_cache`) and eight forms of file (`.claude/settings.local.json`, `CLAUDE.local.md`, `.env`, `.env.local` and `.env.*.local` at the root; a `.pyc` file directly inside a `__pycache__` directory, `.DS_Store` and `Thumbs.db` at any depth), each with its reason beside it; what lies there is local state (last Edge case). A `.gitignore` besides the one at the root that the fingerprint names fails the step too. The step "Working tree unchanged by verification" walks the tree again, so a file that a step leaves outside the list fails the run that wrote it. A file below an embedded repository or a gitlink counts as named: such a tree keeps no fingerprint (AC-2, AC-4).
- A file beside a gate script that carries the name of a standard-library module → never imported: `verify.sh` sets `PYTHONSAFEPATH` for every step, and `scripts/evidence.py` and `scripts/check_baseline.py` restart themselves without their own directory on the module path when started by hand, as the first statements they execute, so a module named `__future__` beside them is never read. A `sitecustomize` module on `PYTHONPATH` runs before any script that is started without `verify.sh`: there `PYTHONPATH` is local state (AC-4).
- An edited fixture generator, or an edited `ave` module that the generator imports, with fixtures of the older code in the cache → generates new files: the cache key of a fixture holds a digest of the three modules of `ave.fixtures` and of every `ave` module that their `import` statements reach, directly or through another module, read from the source text. A module that the generator would load by a computed name lies outside the digest: the diff review judges such a load (AC-2, inspection).
- A test without the `media` marker that calls FFmpeg or FFprobe through `ave.proc` or by name on `PATH` → fails in the fast tier: the fast tier's pytest step points `AVE_FFMPEG` and `AVE_FFPROBE` at a stand-in that exits 1 and puts a directory with `ffmpeg` and `ffprobe` stand-ins first on `PATH`. A test that names a media tool by an absolute path, or that starts a process with a `PATH` of its own, reaches the real tool: `verify-requirement` § 8 judges both forms (AC-3, inspection).
- A cached pass of the Stop gate for a tree whose newest recorded run failed → decides nothing: the gate runs `verify.sh` again (AC-3).
- A run directory prepared before the run, or an old run recorded again → refused: a run starts in a new directory and is recorded once (AC-2).
- A variable of the caller outside the named set (`PATH`, `HOME`, `USER`, `LOGNAME`, `TMPDIR`, `LANG`, `LC_ALL`, `TZ`, `UV_PROJECT_ENVIRONMENT`, `UV_CACHE_DIR`, `UV_PYTHON_INSTALL_DIR`, `AVE_HEAVY_LOCK`, `AVE_HEAVY_LOCK_HELD`) or an exported shell function → reaches no step: `verify.sh` removes them before its steps, sets `PYTHONSAFEPATH`, `PYTHONNOUSERSITE` and `PYTEST_DISABLE_PLUGIN_AUTOLOAD`, and starts `uv` with `--no-env-file`; `GIT_DIR`, `GIT_CONFIG_COUNT`, `PYTHONPATH`, `PYTHONUSERBASE`, `PYTEST_ADDOPTS`, `UV_ENV_FILE`, `AVE_FFMPEG`, `AVE_FFPROBE`, `AVE_VAR_DIR` and `BASH_ENV` are among them. An environment entry whose name is no shell identifier → fails the run before any step (AC-2, AC-4).
- Bytecode, linter and type-checker caches in the tree, a configuration file that a tool finds ahead of `backend/pyproject.toml` (a `ruff.toml` or `.ruff.toml` beside it, a `ruff.toml` or `pyproject.toml` in a directory below, a `mypy.ini` or `.mypy.ini`, a `pytest.ini` or `.pytest.ini`), an ignore file that names a tracked source file (`.git/info/exclude`, an `.ignore` file in the tree or above it), a pytest plugin installed beside the locked packages → change no result: `verify.sh` keeps the bytecode and the type-checker cache of a run in a scratch directory outside the tree, starts ruff with `--config pyproject.toml --no-respect-gitignore --no-cache`, mypy with `--config-file pyproject.toml`, pytest with `-c pyproject.toml -p no:cacheprovider`, and loads no pytest plugin by itself; a verification session selects its tests by marker expression only, so `--deselect` and `-k` under `--forbid-skips` are usage errors wherever the option came from. `uv` finds a `backend/uv.toml` and a `backend/.python-version` ahead of `backend/pyproject.toml`: each is a file of the tree, which the fingerprint names or the step of the Edge case above fails (AC-2, AC-4).
- A tracked file below a directory whose name a tool passes over by itself → takes no part in that tool's step. Each tool keeps a list of its own; measured with the tools of `backend/uv.lock` on 2026-10-07, ruff passes over a directory named `dist`, `venv`, `node_modules`, `_build` or `site-packages` among others, mypy over one named `node_modules`, `site-packages` or `__pycache__` and over one whose name begins with a dot, and pytest collects nothing below one named `dist`, `build`, `venv` or `node_modules` or below one whose name begins with a dot. On 2026-10-07 no tracked path under `backend/` lies below a directory of these names; the diff shows a new one, and the commit review judges it (AC-4, inspection).
- A step file of `scripts/verify.d/` that cannot be loaded → the tier fails; an entry there that is no required file → never sourced, and the "Project control files" step fails (AC-1, AC-4).
- A provider test marked `contract` → never evidences a criterion alone (AC-4). The gate reads the marker: whether a test on a fake carries it is judged by `verify-requirement` § 8 ([ASM-021](../ASSUMPTIONS.md)) (inspection).
- The Stop gate asked for a heavier tier by the environment → still runs the fast tier; an attempt limit outside 1 to 10 → the default 3; a limit of 1 releases at the first failure; a failed-attempt counter that cannot be stored or reads back as another value still ends in a release; a counter file counts when it holds a decimal number of one or two digits, read as decimal also with a leading zero, every other content counts as 0, and the counter stops at 99; a `stop_hook_active` key inside a nested object or a string → decides nothing (AC-3).
- A settings file whose top-level value is no JSON object, without the Stop gate, with a second Stop command, with a Stop handler of another type than `command`, with a key outside the written form (a group of `hooks.Stop` holds `hooks`, a handler `type`, `command` and optionally `timeout`), with a group or a handler that is no object, with a Stop command that differs from `"$CLAUDE_PROJECT_DIR"/.claude/hooks/stop-verify.sh` (text before it, `|| true` or a redirect after it, another spelling of the path), with `disableAllHooks` set to `true`, with a `CLAUDE_VERIFY_` variable, or with `SHELLOPTS`, `BASHOPTS`, `BASH_ENV` or `ENV` in its `env` block → fails check 12 (AC-3). Check 12 reads `.claude/settings.json`; the `timeout` of the Stop handler is judged by the diff review, and `.claude/settings.local.json` and the user-level settings are local state (last Edge case).
- `VERIFY_TIER` exported by the caller → selects the tier and reaches no step, so `VERIFY_TIER=release ./scripts/verify.sh` and `--tier release` give the same result (AC-1).
- A failing step in any tier → that tier fails with exit 1 (AC-1, AC-4).
- An entry point (a `*.sh` file directly under `scripts/`, a hook, a tooling suite or its runner, the media stand-in) without the executable bit on disk or, when tracked, in the Git index → fails check 2 of the "Project control files" step in every tier: a host without executable bits shows every file as executable through the container's mount, while CI checks out the mode the index holds (AC-1).
- A `done` requirement with failed, contract-only or missing evidence → fails the "Done requirements evidenced by this run" step of every tier, the fast tier of the Stop gate included; the release tier, which Definition of Done item 4 requires before `done`, also fails on a tagged test that did not run (AC-4).
- A test or suite whose checks are vacuous (an assertion that cannot fail, a fabricated `TOTAL` line, a test that writes result files itself) → outside the mechanical gate, which sees that checks ran and how they ended: `verify-requirement` § 8 hunts false-positive tests, and Definition of Done item 5 requires its PASS before `done` (AC-4, inspection). Tags of a shell suite count per file; tags of a unit-test file are bound, by class and name, to the test below them: a test of the same name in another class, or a function at module level, leaves the tag unbound and fails the file.
- `record` for a run in a tree without `var/verify/` → creates the directory; where it cannot be created the command ends with status 2 and records nothing (AC-2).
- A criterion evidenced by an inspection line → credited only when its § Verification strategy line names inspection (`- AC-n — inspection — <why>`), and where the strategy names a test level too only beside a tagged test that passed in the run, so the line alone leaves such a criterion missing; `verify-requirement` performs the inspection again and judges it (AC-4, inspection).
- A change to the gate itself (`scripts/verify.sh`, `scripts/verify.d/`, `scripts/lib/verify-state.sh`, `scripts/lib/media-tier-only.sh`, `scripts/evidence.py`, `scripts/reqfile.py`, `scripts/check-project-control.sh`, `scripts/tests/run.sh`, `scripts/dev-container.sh`, `.devcontainer/Dockerfile`, `backend/tests/evidence_plugin.py`, every `conftest.py` under `backend/tests`, the pytest, ruff and mypy configuration in `backend/pyproject.toml`, the hooks, `.claude/settings.json`, the CI workflow) → outside the mechanical gate: the diff shows it, and `verify-requirement` and the commit review judge it (AC-4, inspection).
- Local, unauthenticated state (what lies at the paths of the list of ignored paths, among it `var/verify/` and a fixture that someone wrote into `var/fixtures/` under a valid cache key; `.git/claude-verify/`; the directories above the tree, where a uv workspace that names `backend/` as a member looks for a lock file of its own; the variables `CLAUDE_VERIFY_GATE` and `CLAUDE_VERIFY_MAX_ATTEMPTS`, the interpreter, the shell and the tools on `PATH`, the values of the variables of the named set, the files under `HOME` (the user's Git and uv configuration), `.claude/settings.local.json` and the user-level settings, the shell with what acts before the first line of `verify.sh` (`SHELLOPTS`, `BASHOPTS`, `BASH_ENV`, a function exported under the name of a shell builtin), the files of the backend environment beyond the names and versions of its packages) → outside the mechanical gate and outside every diff: a hand-written manifest or state record certifies nothing, because the run that certifies a requirement is the one the reviewer starts in a private clone, and the run that admits a commit to `main` is CI's on a fresh checkout. On the container host a clone's backend environment is kept per clone path on the state volume, so CI's fresh checkout is the run that covers the environment itself ([ASM-023](../ASSUMPTIONS.md)) (inspection).
